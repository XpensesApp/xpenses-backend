# Xpenses Backend

Serverless expense tracker backend: AWS Lambda + DynamoDB + API Gateway, Python, deployed with AWS SAM (`template.yaml`). Resource names and env vars are resolved per-stage (`dev`/`prod`) via `Mappings` + `!FindInMap` — DynamoDB tables and the Cognito pool are created/owned outside the stack and only referenced.

## Repo layout

- `api/<domain>/<function>/` — only Lambdas exposed as API Gateway endpoints (e.g. `api/transactions/add/` = `POST /transactions`).
- `<function>/` at the repo root — Lambdas that aren't endpoints: `authorizer/` (the Cognito Lambda Authorizer), `billing/` (the scheduled daily subscription billing job) and `statements/` (the scheduled daily credit card statements job).
- `migrations/` — one-off local scripts run against the real tables (never deployed). Dry run by default, `--apply` to write. `credit_cards_2026_10.py` moves existing data to the accounts/transfers/card-statements model: it merges two-movement transfers, generates each card's first statement, and reports duplicates and other suspects.
- `layers/models/` — the shared `ModelsLayer` (models, DynamoDB helpers, HTTP/auth utils), imported by every function.

### `User` — `api/auth/sync/models.py`

### `Transaction` — `layers/models/transaction.py`
| field | type | notes |
|---|---|---|
| `email` | str | owner (table PK), matches `User.email` |
| `title` | str | non-empty |
| `amount` | Decimal | magnitude only; sign comes from `type` |
| `categories` | list[str] | free-form tags, no separate entity |
| `date` | date | |
| `type` | `TransactionType` enum | `EXPENSE` / `INCOME` / `TRANSFER` |
| `affectsBalance` | bool | |
| `pending` | bool | |
| `transactionId` | str | auto (uuid4), part of the sort key |
| `sk` | str | table SK, auto-derived as `"<date>#<transactionId>"` |
| `accountId` | str | an `Account.accountId` of this user; falls back to `"default"` (the user's default account) when omitted |
| `targetAccountId` | str? | destination account; required iff `type` is `TRANSFER` |
| `installments` | int ≥ 1? | for an expense on a credit account: how many monthly statements it's split across (unset = 1) |
| `paymentDay`, `subscriptionId`, `billingPeriod` | optional | |
| `statement` | `CardStatement`? | **server-managed**, only on card statements generated by the statements job (see below) |

**Transfers:** a single `TRANSFER` transaction moves `amount` from `accountId` (or the default account) to `targetAccountId` (required, must differ) instead of recording an expense + an income. It's an outflow for `accountId`, an inflow for `targetAccountId`, and nets to zero on the user's overall balance. `targetAccountId` is rejected on non-transfer types.

**Table key schema:** PK = `email`, SK = `sk`. A single `Query` on `email` returns all of a user's transactions, naturally sortable/filterable by date since `sk` is date-prefixed — no GSI needed for the main use case.

### `Account` — `layers/models/account.py`
| field | type | notes |
|---|---|---|
| `email` | str | owner (table PK), matches `User.email` |
| `accountId` | str | table SK; auto (uuid4 hex) on create, `"default"` for the default account. Referenced by `Transaction.accountId` / `targetAccountId` |
| `name` | str | non-empty |
| `type` | `AccountType` enum | `DEBIT` / `CREDIT` / `CASH` |
| `isSavings` | bool | defaults to `false` |
| `paymentDay` | int (1-31)? | only allowed when `type` is `CREDIT` |
| `openingBalance` | Decimal | defaults to `0`; the balance before any recorded transaction |
| `balance` | Decimal | **server-managed**: `openingBalance` + effect of every settled transaction |
| `transactionCount` | int | **server-managed**: transactions referencing the account (as `accountId` or `targetAccountId`) |
| `isDefault` | bool | **server-managed**: `true` only on the default account |
| `createdAt`, `updatedAt` | datetime | **server-managed** |

Server-managed fields are ignored when a client sends them, and clients can never pick an `accountId`.

**Default account:** every user has one with `accountId: "default"` (fixed, so no lookup is needed), created as `"General"` / `cash` by `ensure_default_account`. `POST /auth/sync` calls it on **every** sync, not only for new users, so users that predate accounts get one on their next login. It's idempotent (`if_not_exists` on every attribute), so a later sync never resets its name or balance. It can be renamed but never deleted. Every transaction without an `accountId` lands there, including the pending ones the billing job generates.

**Which transactions move a balance:** only `affectsBalance: true` **and** `pending: false`. Expense = `-amount` on `accountId`, income = `+amount` on `accountId`, transfer = `-amount` on `accountId` / `+amount` on `targetAccountId`. Every transaction (pending included) counts toward `transactionCount`.

**Consistency:** transaction writes never go straight to the Transactions table. `create_transaction` / `replace_transaction` / `delete_transaction` (in `account.py`) write the transaction item plus every referenced account in one `TransactWriteItems`: `ADD balance, transactionCount` with `attribute_exists(accountId)`, or a plain `ConditionCheck` for a referenced account whose numbers don't change. So they succeed or fail together, a transaction can never reference an account that doesn't exist (→ `400`), and a missing account is never silently created. Edits and deletes also require the stored item's balance fields to still match what was read, so two concurrent edits can't both apply a delta computed from the same stale item (→ `409`). Account deletion is conditional on `transactionCount = 0`, so it can't race with a transaction being added to it. `put_transaction` in `transaction.py` bypasses all of this and is only for local seeding.

**Backfill / repair:** `python layers/models/account.py <email> [...]` or `--all` (needs your AWS credentials and `TRANSACTIONS_TABLE`/`ACCOUNTS_TABLE` env vars) rebuilds `balance` (`openingBalance` + transactions) and `transactionCount` from the user's full history. It also creates the default account, and a placeholder account (name = its id, type `debit`) for any `accountId` that transactions reference but that has no account yet. Run it once after first deploying this, for users who already had transactions. It isn't atomic with live traffic, so run it while the user is idle.

**Table key schema:** PK = `email` (String), SK = `accountId` (String). Created outside the stack (like every table here), referenced via `TableNames.AccountsTableName`.

### `Subscription` — `layers/models/subscription.py`
| field | type | notes |
|---|---|---|
| `email` | str | owner (table PK), matches `User.email` |
| `title` | str | non-empty |
| `billingDay` | int (1-31) | day of month a pending `Transaction` is generated |
| `type` | `TransactionType` enum | reused from `transaction.py` — a salary is an income subscription; `TRANSFER` is rejected (subscriptions have no accounts) |
| `affectsBalance` | bool | |
| `status` | `SubscriptionStatus` enum | `ACTIVE` / `DISABLED` |
| `subscriptionId` | str | auto (uuid4), table SK |
| `amount` | Decimal? | unset = variable/unknown (e.g. electricity) until billed |
| `categories` | list[str] | defaults to `[]` |
| `createdAt` | datetime | defaults to now |
| `endDate` | date? | optional expiration |

**Table key schema:** PK = `email`, SK = `subscriptionId` (plain, not composite — no in-partition ordering is needed for "list a user's subscriptions"). GSI `BillingDayStatusIndex` (PK=`billingDay`, SK=`status`, projects all attributes) serves the cross-user daily-billing lookup — `Query(billingDay=today, status=active)` — independent of the base table's own keys.

`generate_transaction_from_subscription(subscription, billing_date)` (in `subscription.py`) converts a subscription into its pending `Transaction`: carries over `amount` (or `Decimal("0")` if unset), always `pending=True`, and builds a **deterministic** `transactionId` (`f"{subscriptionId}-{date}"`) so reprocessing the same subscription/date hits the same key, and the job's conditional insert skips it rather than duplicating or overwriting it (which would clobber a bill the user already settled). This is the idempotency mechanism the daily billing job relies on.

## Endpoints

**`POST /auth/sync`** — verifies a Cognito ID token (Bearer header) against the pool's JWKS, then looks up the user by email in the Users table and creates it if it doesn't exist yet. Also ensures the user's default account exists (see `Account`).

**Transactions CRUD** (`api/transactions/{add,get,edit,delete}`) — **protected** by `CognitoAuthorizer` (see below). `email` comes from the verified token, not the request — dropped from the contract entirely:
- `POST /transactions` — create (`409` if the client-supplied `transactionId` + `date` already exists)
- `GET /transactions?from=&to=&limit=&nextToken=` — list the caller's own records in a date range (defaults to the last month), newest first, paginated; the response echoes the applied `dateRange` and a `nextToken` cursor (null on the last page). The range maps to a `BETWEEN` on the date-prefixed `sk`, so cost scales with the range, not the user's full history
- `PUT /transactions` (needs `transactionId`) — full-replace update. Changing `date` moves the item: the date is part of its key, so if nothing exists under the body's date it's found by `transactionId` (a full read of the user's partition, only in that case), then deleted and re-created under the new key in one atomic write. A card statement's date can't be changed (`400`)
- `DELETE /transactions?transactionId=&date=` — delete

Create/update/delete also update the referenced accounts atomically (see `Account` above): `400` if an `accountId`/`targetAccountId` doesn't exist, `409` on update/delete if the transaction changed concurrently.

**Accounts CRUD** (`api/accounts/{add,get,edit,delete}`) — **protected** by `CognitoAuthorizer`, same rule as Transactions:
- `POST /accounts` — create (server generates `accountId`; `balance` starts at `openingBalance`)
- `GET /accounts` — all of the caller's accounts in one response (no paging), default account first, then oldest first
- `PUT /accounts` (needs `accountId`) — full replace of the editable fields; changing `openingBalance` shifts `balance` by the same difference
- `DELETE /accounts?accountId=` — `400` for the default account, `409` while `transactionCount > 0`

**Subscriptions CRUD** (`api/subscriptions/{add,get,edit,delete}`) — **protected** by `CognitoAuthorizer` too, same rule as Transactions:
- `POST /subscriptions` — create
- `GET /subscriptions` — list the caller's own records, newest first
- `PUT /subscriptions` (needs original `subscriptionId`) — full-replace update
- `DELETE /subscriptions?subscriptionId=` — delete

Open CORS (`*`) on every route.

## Credit Card Statements Job

`statements/app.py` (`CardStatementsFunction`) runs on an EventBridge schedule (`cron(15 6 * * ? *)`). The rules live in `layers/models/statement.py` (pure functions, no I/O); the job only does the reads and writes.

**Model.** A card purchase is an `expense` on a credit account, split across `installments` monthly statements (unset = 1). It moves the card's balance by the full amount at purchase time, so the card balance is its debt. Each month the job generates **one pending `transfer` per card**, from the default account into the card (paying the card), with `transactionId` `statement-<cardId>-<date>` and a `statement` breakdown:

| field | notes |
|---|---|
| `statement.accountId` | the card |
| `statement.lines` | `{transactionId, title, date, installment, installments, amount}` for every installment due this month |
| `statement.installmentsDue` | sum of `lines` |
| `statement.previousBalance` | still owed from before this statement's `lines`; negative = credit from an overpayment |
| `statement.amountDue` | `installmentsDue + previousBalance`; the transaction's `amount` is this, floored at 0 |
| `statement.since` | the card's first statement date (inherited along the chain) |
| `statement.revision` | bumped on every recalculation; guards concurrent recalculations |

**Schedule.** The due date is the card's `paymentDay`, clamped to the month's length (31 → Feb 28/29). A purchase dated before a due date is first billed on it; one dated on the due date itself or later goes to the next month. Installment *k* is billed on the *k*-th due date from there. Installment amounts are equal and rounded down to the purchase's precision, with the remainder on the last one, so they always add up to the purchase amount.

**Amounts are a closed form, not a running total**, so any statement can be recalculated from the stored data at any time: `amountDue(D)` = every installment due on a date in `[since, D]` minus every payment dated in `[since, D)`. `since` is the card's first statement date; installments due before it are assumed paid outside the app. Payments are settled, balance-affecting transfers into the card (paid statements included) and incomes on the card (refunds). That way partial, multiple and late payments and overpayments all carry forward. A payment dated after a statement's date counts toward the next one. Breakdown: `lines` are the installments due after the latest **settled** statement (or from `since`), and `previousBalance` is the rest of `amountDue`.

**Lifecycle** (`plan_statement` / `sync_card_statement`). Only the statement for the card's most recent due date is ever created or recalculated. **Settled statements never change**: an edit to a purchase they covered surfaces in the next statement's `previousBalance`. An older statement still pending when the next one is created is rolled over: it's deleted in the same atomic write (`account.swap_transactions`), and its amount is already included in the new one. So a card has at most one pending statement.

**Recalculated on every write.** After each `POST`/`PUT`/`DELETE /transactions`, `sync_cards_touched_by` recalculates the pending statement of every credit card the old or new version touches (as `accountId` or `targetAccountId`). It creates the statement if a purchase just made something due, updates it, or deletes it if nothing is due anymore. User-set fields on a pending statement (`title`, `categories`, the paying `accountId`) are kept, but its `amount` is always the computed one. Writes are conditional on the statement's `revision` and re-read and retried on conflict, so concurrent recalculations can't leave a stale result. It's best-effort: the transaction is already saved, so a failure is logged instead of failing the request, and the daily job repairs it. A pending statement can't be deleted (`400`); a settled one can (that undoes the payment).

**Paying.** `PUT /transactions` on the statement with the amount actually paid, `pending: false` and the paying `accountId`. The edit handler keeps a statement's `type`, `targetAccountId` and `statement` breakdown from the stored item whatever the body says, and `POST /transactions` drops any client-sent `statement`. So clients can't forge or break the carry-over chain.

**Run logic.** For each credit account (a filtered `Scan`: the Accounts table is tiny, and a sparse `paymentDay` GSI would need `paymentDay` omitted rather than NULL on non-credit accounts), the daily job runs the same `sync_card_statement` for the **most recent** due date ≤ today, using the user's full transaction history (read once per user per run). That makes it self-healing: a missed/failed run, a card added after its due date, or a recalculation the API couldn't finish is caught up on the next run. Cards with nothing due and nothing owed get no statement. Credit accounts without a `paymentDay`, or that are the default account, are skipped. Idempotent (deterministic ids, conditional writes, up-to-date statements aren't rewritten). Pass `{"date": "YYYY-MM-DD"}` to run as of another day. Returns/logs `{date, create, update, delete, settled, none, skipped, failed}`.

**Cost note:** each recalculation reads the user's full transaction history, so writes touching a card get slower as history grows. Bounding the read (e.g. to `since` minus the longest installment plan) is the fix when that matters.

## Cognito Lambda Authorizer

`authorizer/app.py` (`CognitoAuthorizerFunction`) is a `TOKEN`-type REST API authorizer, wired onto every Transactions, Accounts and Subscriptions route (`XpensesApi`'s `Auth.Authorizers.CognitoAuthorizer` — no `DefaultAuthorizer`, so `/auth/sync` stays on its own inline check unless a route opts in via `Events.*.Properties.Auth.Authorizer`).

It reuses the exact same verification `auth/sync` does inline (`cognito_auth.py` in the shared layer — extracted from `auth/sync/app.py` specifically so this wouldn't be a third copy). On success it returns an Allow policy plus `context: {email}`, which lands on the downstream Lambda's event at `requestContext.authorizer.email` (read via `http_utils.get_authenticated_email(event)`). On failure it raises the exact string `"Unauthorized"` — the API Gateway TOKEN-authorizer contract that produces a 401 (any other exception message/type produces a 500 instead). That 401's body is customized via `GatewayResponseDefault4xx` in `template.yaml`, **not** a dedicated `GatewayResponseUnauthorized` (`ResponseType: UNAUTHORIZED`) — confirmed empirically that `UNAUTHORIZED` genuinely never applies to this failure mode, while `DEFAULT_4XX` does (an earlier test on `DEFAULT_4XX` gave a false negative from testing only seconds after patching, before the change had propagated). Safe to put an auth-specific message on that catch-all since our own Lambda-level 400/404 responses never go through `GatewayResponse` at all. The real per-request reason (expired, bad signature, wrong issuer, ...) still only goes to CloudWatch (`auth-authorizer-{stage}`), never the client — genuinely dynamic per-request messages aren't achievable here regardless, short of migrating the REST API to an HTTP API (v2). `Identity.ReauthorizeEvery: 300` caches a decision for 5 minutes per token; the returned policy's `Resource` is wildcarded to the whole API stage so that cache applies across routes, not just whichever one triggered the check.

**Ownership, not just authentication:** a valid token alone isn't what makes these routes safe — every handler calls `http_utils.get_authenticated_email(event)` and uses *that* (never a client-supplied value) as the DynamoDB partition key for every read/write. `edit`/`delete` build their lookup key from the token's email plus the client-supplied resource id, so trying to edit/delete someone else's `transactionId`/`subscriptionId` just misses (`404`, not their data) — there's no separate "does this belong to you?" check, ownership is enforced by construction: the key can only ever resolve to your own partition.

## Daily Billing Job

`billing/app.py` (`DailyBillingFunction`) runs on an EventBridge schedule (`cron(0 6 * * ? *)` — 06:00 UTC, adjust in `template.yaml` to taste). Each run: `Query`s `BillingDayStatusIndex` for `billingDay == today`, `status == active` (paginated), skips anything already `endDate`-expired, and inserts a pending `Transaction` for everything else via `generate_transaction_from_subscription` + `create_transaction`. A transaction that already exists for that subscription/date is left untouched and counted in `alreadyBilled`. Safe to re-invoke for the same day (idempotent) or a past day for backfill — pass `{"date": "YYYY-MM-DD"}` as the event payload to override "today". Returns/logs a `{date, created, alreadyBilled, skippedExpired, failed}` summary; a single malformed subscription is caught and counted in `failed` rather than aborting the whole run.

## Getting a Test Token

`api/auth/sync/get_test_token.py` — **local-only dev tool, never deployed**. The Cognito pool supports native (non-Google) sign-in alongside Google, so a dedicated test user (`test@xpenses.dev`) logs in with a real username+password via Cognito's `USER_AUTH` flow and gets back a real ID token — same issuer/audience/claims a Google-authenticated user would get, so it passes `verify_token()` and works against any protected endpoint. Requires your own AWS credentials to run (only whoever has access to this account can mint a token this way):

```bash
cd api/auth/sync
AWS_PROFILE=personal python get_test_token.py
```

Needs `COGNITO_APP_CLIENT_SECRET` and `TEST_USER_PASSWORD` in `.env` (the app client has a secret, so Cognito requires a `SECRET_HASH` on every auth call). Deliberately not exposed as a deployed endpoint — every current route is unprotected, so a token-minting endpoint on this same API would be reachable by anyone. When a dev/prod split exists, a real `POST` endpoint for this is planned, but gated to the dev stage only and still requiring real username+password (not free token issuance for arbitrary emails).

## Shared Lambda Layer

`layers/models/` (`transaction.py`, `subscription.py`, `http_utils.py`, `cognito_auth.py`) is a real Lambda Layer (`ModelsLayer` in `template.yaml`), attached to each transactions/subscriptions function via `Layers:`. `sam build` nests it under `python/` automatically so it lands on `/opt/python` at runtime.

Locally, that folder isn't on `sys.path` by default, so running any Lambda's `if __name__ == "__main__"` block directly needs `PYTHONPATH` pointed at it:

```bash
# from inside e.g. api/transactions/add/
PYTHONPATH=../../../layers/models python app.py
```

PowerShell:
```powershell
$env:PYTHONPATH = "..\..\..\layers\models"; python app.py
```

Each `__main__` block runs against a fixed test user (`jane@test`) and your real `.env` (`USERS_TABLE`, `TRANSACTIONS_TABLE`, `SUBSCRIPTIONS_TABLE`, `COGNITO_*`), loaded via `python-dotenv`. For the (now-protected) Transactions Lambdas, the `__main__` block simulates the authorizer's output directly (`event["requestContext"]["authorizer"]["email"]`) rather than needing a real token — use `api/auth/sync/get_test_token.py` when you need to exercise the real deployed/protected route end-to-end instead.
