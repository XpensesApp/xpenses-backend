# Transactions Endpoints — Frontend Handoff

Base URL: the API Gateway stage URL for the deployed stack (SAM output `ApiUrl`), e.g. `https://{api-id}.execute-api.{region}.amazonaws.com/{stage}`.

**These 4 endpoints are now protected** by a Cognito Lambda Authorizer — every request needs a real, valid Cognito ID token:

```
Authorization: Bearer <cognito-id-token>
```

`email` is derived from the verified token — **it is no longer accepted anywhere in the request** (not in the body, not as a query param). A caller can only ever read/write their own data; there's no way to act on someone else's records even by trying to pass a different email.

Missing/invalid/expired token → `401` (`{"message": "Missing, invalid, or expired authentication token..."}`) before your Lambda-side code even runs — this is API Gateway's own error response, not one of ours.

CORS is still open (`*`) on all of them.

All responses are `Content-Type: application/json`.

---

## `Transaction` object shape

Every endpoint below sends/returns this shape (all keys always present; unset optionals are `null`):

```json
{
  "email": "jane@test",
  "title": "Groceries",
  "amount": "45.90",
  "categories": ["food", "household"],
  "date": "2026-09-14",
  "type": "expense",
  "affectsBalance": true,
  "pending": false,
  "transactionId": "01562af501d74fb9b5b9f4979c3b476d",
  "sk": "2026-09-14#01562af501d74fb9b5b9f4979c3b476d",
  "accountId": null,
  "targetAccountId": null,
  "installments": null,
  "paymentDay": null,
  "subscriptionId": null,
  "billingPeriod": null
}
```

Notes:
- `email` still appears in the response (it's stored on the item) — it's just no longer something *you* provide; it always matches whoever the token belongs to.
- `amount` is a **string** (e.g. `"45.90"`), not a JSON number — parse it as a decimal on the frontend to avoid float rounding. It's always positive when `pending` is `false`; `type` gives direction (`"expense"` subtracts, `"income"` adds). A `pending` transaction (e.g. one generated by a subscription with a variable/unknown amount) may have `amount: "0"` until it's settled.
- `type` is one of `"expense"` | `"income"` | `"transfer"`.
- **Transfers:** `type: "transfer"` moves `amount` from `accountId` to `targetAccountId` in one record (no need for an expense + an income). Both are required and must differ. Treat it as an outflow for `accountId`, an inflow for `targetAccountId`, and exclude it from expense/income totals (it nets to zero on the overall balance). `targetAccountId` is `null` for any other type, and sending it with a non-transfer type is a `400`.
- `date` is `"YYYY-MM-DD"`.
- `transactionId` and `date` are what you need later to edit/delete a transaction.
- `sk` is an internal DynamoDB sort key. Treat it as opaque — don't construct or rely on it; use `transactionId` + `date` instead.
- `subscriptionId`/`billingPeriod` are set on transactions the daily billing job generates from a subscription; `null` for manually-created ones.

## `POST /transactions` — create

**Request:** JSON body with the required fields. No `email` — do not send it, it's ignored even if present. Omit `transactionId`/`sk` (auto-generated).

```json
{
  "title": "Groceries",
  "amount": "45.90",
  "categories": ["food", "household"],
  "date": "2026-09-14",
  "type": "expense",
  "affectsBalance": true,
  "pending": false
}
```

Required: `title` (non-empty), `amount` (> 0, or `0` only if `pending: true`), `categories` (array of strings, can be empty), `date`, `type` (`"expense"`/`"income"`/`"transfer"`), `affectsBalance`, `pending`.
Optional: `accountId`, `targetAccountId` (both **required** when `type` is `"transfer"`, and must differ), `installments` (int ≥ 1), `paymentDay` (int 1–31), `subscriptionId`, `billingPeriod`.

**Response:**
- `201` — the created transaction (full shape above, owner = whoever the token belongs to).
- `400` — `{"message": "Invalid transaction: ..."}` on missing/invalid fields.
- `401` — missing/invalid/expired token.

Transfer example:

```json
{
  "title": "Move to savings",
  "amount": "200.00",
  "categories": [],
  "date": "2026-10-03",
  "type": "transfer",
  "affectsBalance": true,
  "pending": false,
  "accountId": "checking",
  "targetAccountId": "savings"
}
```

## `GET /transactions` — list

**Request:** no query params, no body — just the Authorization header.

```
GET /transactions
```

**Response:**
- `200` — `{"transactions": [ <Transaction>, ... ]}` for the token's owner, newest first (sorted by `date`).
- `401` — missing/invalid/expired token.

---

## `PUT /transactions` — update (full replace)

**Request:** JSON body with **every** field, not just the ones changing — this replaces the stored item rather than patching individual attributes. Must include the transaction's original `transactionId` and `date` so the backend can find it. No `email`.

```json
{
  "title": "Groceries (updated)",
  "amount": "50.00",
  "categories": ["food"],
  "date": "2026-09-14",
  "type": "expense",
  "affectsBalance": true,
  "pending": false,
  "transactionId": "01562af501d74fb9b5b9f4979c3b476d"
}
```

**Response:**
- `200` — the updated transaction (full shape above).
- `400` — `{"message": "transactionId is required to identify the transaction to edit"}` (missing) or `{"message": "Invalid transaction: ..."}` (bad fields).
- `404` — `{"message": "Transaction not found"}` if no item matches (the token owner + the reconstructed key).
- `401` — missing/invalid/expired token.

---

## `DELETE /transactions?transactionId=...&date=...` — delete

**Request:** query string only, no body. Both params required. No `email` param.

```
DELETE /transactions?transactionId=01562af501d74fb9b5b9f4979c3b476d&date=2026-09-14
```

**Response:**
- `200` — `{"message": "Transaction deleted"}`.
- `400` — `{"message": "Missing required query parameters: transactionId, date"}`.
- `404` — `{"message": "Transaction not found"}`.
- `401` — missing/invalid/expired token.
